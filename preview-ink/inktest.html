#baseInk — Safari self-test

Diagnostic page. Not the map, not the app. Nothing here is installed or cached.

Do this: read section 1 below, then screenshot the whole page (two shots if it doesn’t fit) and send them back. Everything on this page states what it should look like, so nothing needs to be judged by eye.

1 · The one question

The card below has two lines of text on it, in two colours the filter pushes in opposite directions. Whatever happens, exactly one of them is readable — the other is the same colour as the paper.

MARLIN 42
FILTER IS DEAD

Which line can you read?
“MARLIN 42” → the filter is alive in Safari.
“FILTER IS DEAD” → Safari is dropping it, exactly as feared.
Read me the line, that’s all. You aren’t judging a shade or comparing two loads — one of those two phrases is sitting there in plain grey or plain brown, and it names the answer. If you can also make out a faint ghost of the other line, ignore it: go by the one that is actually dark enough to read at a glance.

2 · Colour swatches (k = 6)

Same colours USGS actually paints, pushed far past the clip point. On a working renderer these are not subtle — water goes black, land goes white.

A · water, no filterreference only stays pale blue
B · water + url(#…)the production construct should be BLACK
C · land, no filterreference only stays pale green
D · land + url(#…)should be WHITE
E · water, url() + contrast()exactly how production writes it should be BLACK
F · water, EXTERNAL .svgfallback #1 should be BLACK
G · water, plain CSS filtercontrol — no url() involved should be DARK GREY
H · water, filter INSIDE svgcontrol — not the CSS path should be BLACK

If B is black but the map looked unchanged, the filter is fine and the map comparison was just made between values too close together. If B is still pale blue while G is dark grey, Safari supports CSS filters but is dropping the url() reference — that is the failure case.
